# 微信支付自动入账 · 可行性分析

> 面向奶蛙记账（cash-diary）的落地评估。写于2026-10-12。
> 结论都标了来源：**[官方]** = 微信支付官方文档写明的；**[社区]** = 开源项目/博客方案，未经官方背书；**[推断]** = 我的判断，需要你自己再验。

---

## 0. 一句话结论

**没有任何一条路能做到「用户什么都不做，每笔微信支付实时自动入账」。**

能做到的最好形态是：**用户在 App 里点一下「导入微信账单」，选一个刚导出的 CSV 文件，App 解析并生成一批账目**。这是唯一合规、稳定、且不破坏「数据只存本地」定位的方案。

想要更接近「实时」，得走系统通知监听，但它是**概率性**的（漏单、误判、厂商 ROM 杀后台），而且需要引入原生插件 —— 你现在的打包链是纯 uni-app，没有原生插件，这是一笔额外的架构成本。

---

## 1. 官方能力盘点：为什么个人用户「一个都调不通」

### 1.1 微信支付 API 的定位是「商户收单管理」[官方]

查订单接口（`GET /v3/pay/transactions/id/{transaction_id}`）的必填参数：

| 参数 | 是否必填 | 说明 |
|---|---|---|
| `mchid`（商户号） | **是** | query 参数，没有商户号直接 400 |
| `appid` | 是 | 必须是**已绑定该商户号**的 appid |
| `Authorization` | 是 | `WECHATPAY2-SHA256-RSA2048` 签名，需要商户 API 私钥 |
| API 证书序列号 | — | 商户平台下载 |

**这不是「查询你的微信支付记录」，这是「查询你自己店铺收到的订单」。** 语义完全不同。

### 1.2 支付结果回调 —— 只推给你自己的商户订单

`回调通知`的接收地址是在商户平台配的（`notify_url`），微信只会把**通过你家 appid 下单**的交易推给你。你在超市扫码付的钱，跟你的商户号没有任何关系，微信不会推给你 —— 因为它压根不知道你要知道。

**边界**：商户只能看到「谁在我的店里付了钱」，看不到「这个人还在别处花了多少钱」。

### 1.3 账单文件下载 —— 按商户号生成

`/v3/bill/tradebill?bill_date=xxx&mchid=xxx`[官方]：

- 以**商户号**为维度生成，一个商户号绑多个 appid 也只出一份
- **仅支持三个月内**
- 次日 10点后可取前一日账单，下载地址 30秒内有效
- 金额单位是「元」（字符串），不是分

同样调不通。

### 1.4 那个人能拿到什么？只有「账单导出」[官方]

这条路是官方开给个人的，路径：

```
微信 → 我 → 服务 → 钱包 → 账单 → 右上角「…」→ 下载账单 → 用于个人对账
```

关键限制（全部 [官方]）：

| 项 | 值 |
|---|---|
| 文件格式 | Excel / CSV（个人对账不加公章） |
| 是否含已删除记录 | 含 |
| 导出区间 | 每次最长一年 |
| 接收方式 | 微信支付服务号 或 邮箱，**每次申请只能二选一** |
| 下发时效 | 24 小时内（实际通常几分钟到半小时） |
| 服务号下载有效期 | **7 天**，过期要重新申请 |
| 邮箱 | 无有效期限制 |
| 验证 | 只有实名本人，需刷脸；无法刷脸可用 姓名+身份证+支付密码 |

> ⚠️ 注意最后一行：**这是需要人脸/支付密码的敏感操作**，不可能做到「App 静默自动拉取」。

### 1.5 有没有「个人订阅账单推送」这种能力？

搜了一圈，**没有**面向个人的账单自动推送/订阅接口。[推断：基于官方文档目录，微信支付开放平台只覆盖商户侧，没有 C端账单订阅能力。]

## 2. 四条路线横向对比

| 路线 | 实时性 | 合规性 | 稳定性 | 开发成本 | 需联网 | 结论 |
|---|---|---|---|---|---|---|
| **A. 官方支付 API** | 实时 | ✅ | ✅ | — | ✅ | ❌ **不可行**，必须商户号 |
| **A'. 账单文件 API** | T+1 | ✅ | ✅ | — | ✅ | ❌ **不可行**，必须商户号 |
| **B. 账单 CSV 导入** | 手动（分钟级） | ✅ | ✅ 高 | 中（2-4 天） | ❌ | ✅ **推荐主线** |
| **C. 通知监听** | 近实时（秒级） | ⚠️ | ⚠️ 中低 | 高（1-2 周+） | ❌ | 🟡 **可选补充** |
| **D. 无障碍/OCR 兜底** | 近实时 | 🔴 | 🔴 低 | 很高 | ❌ | ❌ **不建议** |

### 关于 D 为什么劝退

社区有方案用 `MediaProjection` 截通知栏 + TensorFlow Lite OCR 识别金额[社区]。但：
- Android 12 起 `NotificationListenerService` 默认被系统限制
- 需要无障碍服务 + 通知使用权 + 存储权限 三件套
- OCR 会认错数字，记账场景认错金额是致命的
- 开源方案自己都写了免责声明[社区]

如果已经上了 C，OCR 没有任何增量价值。

### 关于 C 的真实代价（必须知道）

uni-app **没有内置通知监听能力**。要在你的 App 里监听微信通知，必须写 **Android 原生插件**（UTS 插件 或 原生 App 自定义基座）。

这意味着你现在的链路要改：

```
现状：HBuilderX 云打包（纯 uni-app，无原生插件）
新增：→ 本地打包 / 自定义基座 + 原生模块
      → manifest.json 加 app-plus.distribute.modules.nativePlugins
      → ⚠️ 正式包不再读外置 www → 验 App 端必须重新云打包/本地打包
      → ⚠️ 每次原生插件变更，wgt 热更**失效**（原生代码在apk 里）
```

**这条对本项目是硬伤**：你的发版链（wgt 热更 + 云打包）目前很顺畅，加原生插件会把「改一行 JS 就能热更」的优势彻底废掉。每次改一行解析逻辑都要重新出包。

## 3. 推荐方案：B路线 —— 账单导入

### 3.1 用户流程

1. 用户按官方路径导出微信账单（去微信操作，App 教他做）
2. 把CSV 传到手机（微信文件传输助手 / 数据线 / 或直接从邮件下载）
3. App 内点「导入微信账单」→ 选文件 → 解析 → **先展示导入预览**
4. 用户确认 → 批量写入

> 体验上离「自动」差一步，但可靠得多。而且 CSV 里带**交易单号**，可以精确去重，重复导入同一个文件不会重复记账。

### 3.2 CSV 格式（已核实）

[社区，但多家开源项目格式描述一致，可信]

- 编码：**UTF-8**
- 前 **16 行**是元信息（导出信息、姓名、统计说明、分隔线）
- **第 17 行**是表头
- 第 18 行起是数据
- 11 列：

```
交易时间, 交易类型, 交易对方, 商品, 收/支, 金额(元),
支付方式, 当前状态, 交易单号, 商户单号, 备注
```

> ⚠️ 未确认项：XLSX（Excel）格式的内部结构是否有差异，需实测。我建议**只支持 CSV**，XLSX 在 uni-app 里解析要引库，性价比低。

### 3.3 字段映射到你的 schema

| CSV 列 | 映射到 | 处理方式 |
|---|---|---|
| `交易单号` | 新字段 `ext_ref` | **天然唯一键，去重靠它** |
| `交易时间` | `occurred_at` | `2026-10-05 14:23:11` → 毫秒戳，注意**不要用 `Intl`/`new Date(str)`**（App 端解析差异大），按 `date.js` 现有方式手工切分 |
| `金额(元)` | `amount_cents` | 元→分：`Math.round(parseFloat(s) * 100)`。**注意浮点**，建议用字符串切分（取小数点后两位转整数）而不是乘 100 |
| `收/支` | `direction` | `支出` / `收入`（不含 `/` 的直接是收支，`/` 开头如 `/ refunded` 单独处理） |
| `当前状态` | 过滤 + 退款标识 | `支付成功`、`已退款`、`交易关闭`、`已全额退款` |
| `交易对方` | 备注（截断） | 商户名。**建议截断到 20 字**，有些字段超长 |
| `交易类型` | 自动分类输入 | 见 3.5 |
| `商品` | 备注补充 | 一般为空 |
| `商户单号` | 丢弃 | 商户侧编号，对用户无意义 |
| `支付方式` | 可选存account 映射 | `零钱`/`零钱通`→ 余额账户，`招商银行(1234)` → 可选引导建银行卡账户 |
| `备注` | 丢弃 | 用户手填内容，可能是隐私 |

### 3.4 状态过滤规则（这一步决定数据质量）

**必须丢掉的**：

| 当前状态 | 原因 |
|---|---|
| `交易关闭` | 订单未成交。社区方案都专门丢这条[社区] —— 这类订单可能已在其他渠道付过，留着会重复 |
| 金额为 0 | 占位行 |
| `已退款` / `已全额退款` | 见下|

**退款怎么处理 —— 这是最容易做错的地方：**

| 情况 | 处理 |
|---|---|
| 一笔支出，后来全额退款 | 原始那笔 **软删**（`deleted_at`），退款那笔不入账 → 净支出 0，✅ 正确 |
| 一笔支出，后来部分退款 | 保留原支出，另生成一笔**收入**（金额=退款额）→ 净支出减少，✅ 正确 |
| CSV 里直接出现 `-12.50` 的负数行 | **直接丢弃**，因为原支出那行还在，留着会双扣 |

> ⚠️ 这里有个真实的坑：微信 CSV 里退款是**独立行**，`交易单号` 与原交易**相同**、`当前状态`标 `已退款`。所以去重键要用 `交易单号 + 当前状态 + 金额` 组合，不能只用交易单号。

### 3.5 自动分类规则

你已经有 12 个一级分类 + 37 个二级。微信的 `交易类型` 列本身就能覆盖一部分[社区]：

| 微信交易类型 | 建议映射到 |
|---|---|
| 商户消费 | 餐饮/ 交通 / 购物 / 娱乐（需按商户名细分） |
| 扫二维码付款 | 同上 |
| 理财 | ❌ 不记账（不是消费） |
| 信用卡还款 | ❌ 不记账（这是账户间转移，会重复） |
| 转账 | 收入/ 其他 |
| 红包 | 其他 / 人情 |
| 生活缴费 | 居住 |
| 退款 | 收入 |

**商户消费才是大头**，靠`交易对方`（商户名）做关键词匹配。建议做成**规则表 + 用户可编辑**：

```javascript
// services/import-rules.js（新建）
const RULES = [
  { kw: ['美团', '饿了么', '肯德基', '麦当劳', '星巴克', '瑞幸', '蜜雪'],
    catId: 'dining', level: 1 },
  { kw: ['滴滴', '地铁', '公交', '高德', '12306', '中国铁路', '航空', '停车'],
    catId: 'transport', level: 1 },
  { kw: ['超市', '永辉', '沃尔玛', '家乐福', '便利店'],
    catId: 'groceries', level: 1 }
  // ...
]
```

匹配顺序：先精确命中 → 再关键词 → 都没命中落到 `other`，**并在导入预览里高亮未分类项让用户批量指定**。

> 别学`AutoBookKeepingBeta` 那种把原始通知文本丢给云端 LLM 解析的做法[社区] —— 那要联网、要上传文本，直接破坏你「数据不出本地」的卖点。

### 3.6 与你现有架构的对接

按 AGENTS.md 的分层来，新加四层：

```
services/wechat-bill.js      // 解析 CSV → 标准化中间结构
services/import-rules.js      // 关键词 →分类
db/bill-import-sql.js        // 查已存在的交易单号（批量去重）
services/tx.js: importBatch() // 批量写入
```

**需要新增的表列（改四处，别忘了）**：
- `schema.js: MIGRATIONS` 加一条 v8迁移，`ALTER TABLE transaction_record ADD COLUMN ext_ref TEXT`
- `sqlite.js: TABLE_COLS` 加 `ext_ref`
- `memory.js: TABLES` 同步
- 两侧 `clearAll` 不涉及（新列不用清）

> ⚠️ `tests/schema.test.js` 的版本数组是**精确相等**断言，加迁移必须同步改。
>
> ⚠️ 另加一个 `ext_ref` 索引，否则去重查询在流水多了之后会全表扫。

**触发时机设计（回答「实时性」）**：
批量导入没有「实时」概念，触发点就是**用户点导入那一刻**。所以去重只需要在导入开始时查一次已存在的 `ext_ref` 集合即可，不用做增量对账。

### 3.7 去重与失败重试

- **去重**：`ext_ref` + `(交易单号, 当前状态, 金额)` 组合，查 `ext_ref IN (...)` 已存在的直接跳过
- **事务**：整个导入包在一个事务里，失败全回滚。不要一半成功一半失败 —— 用户没法判断哪些进去了
- **重试**：本地 SQLite 写入失败基本只有两种（磁盘满、库被锁），让用户重试即可，不需要队列式重试
- **预检**：先解析完 → 用**你现有的 `plus.sqlite` 无参数绑定风格**在内存里算出「将新增 N 笔 / 跳过 M 笔」→ 展示确认页 → 才写库

### 3.8 隐私与安全

| 项 | 处理 |
|---|---|
| CSV 文件 | 导入完**立刻删除**（`plus.io` 删文件，注意你项目里已有的 `createReader()` 在 vivo/OriginOS 永久挂起的坑，套 `withTimeout()`） |
| 商户名 / 商品 | 属于用户消费隐私，**只存本地**，不进任何日志、不上传 |
| `交易单号` | 不是敏感凭证，但它是唯一标识，存明文可接受（本地库，且你现有备份是明文 JSON） |
| openid | ❌ **个人账单 CSV 里根本没有 openid**。只有官方 API 才会返回 `payer.openid`。所以这个字段对你不适用，不存在泄露风险 |
| 权限申请 | 读文件只需沙盒内路径，**不需要申请存储权限**（Android 11+ 用系统文件选择器 SAF 更安全，别申请 `MANAGE_EXTERNAL_STORAGE`） |
| 合规 | 账单是用户自己的数据，用户主动导出自己给自己用，无合规风险。**不要**帮用户做「自动抓取他人账单」类功能 |

## 4. 如果要做 C（通知监听），代价清单

放这里是为了让你知道**完整的坑**，不是推荐做。

### 4.1 需要的能力

```
NotificationListenerService        // 系统通知监听（需用户手动开「通知使用权」）
+ 前台服务常驻                // 否则被杀掉
+ 厂商白名单引导（小米/华为/vivo/OPPO 各一套）
+ 原生插件（uni-app 没有，得写 UTS 插件或自定义基座）
```

### 4.2 通知文本长什么样（社区方案实测格式）[社区]

```
标题：微信支付
内容：微信支付凭证 · 付款给xxx ¥12.50
```

`寄帐` 这个项目解析的是 `¥12.50` 模式[社区]。实际到账通知还会变：

```
收款 ¥12.50          ← 省略了付款人
已收款 ¥12.50，在商家 xxx 付款  ← 句式变了
微信支付凭证 付款12.50元  ← 没有 ¥ 符号
```

**这些格式我未逐一核实**，你必须自己在真机上抓一遍。

### 4.3 硬伤

- **通知不保证有**：微信/QQ/淘宝可以在设置里关闭通知；厂商省电策略可能拦截
- **通知不是账目凭证**：转账、红包、收款、退款混在一起，需要靠 `sbn`（通知包名）+ 关键词区分
- **去重困难**：通知没有唯一单号，只能靠「金额 + 时间窗口 + 商户名」模糊去重 —— 同一天买两杯 15 元的咖啡会丢一笔
- **HyperOS 封锁**：你自己项目里已经验证过，小米 HyperOS 3.0 封锁了 `input tap`/`pm grant`，后台服务被杀得很凶[项目记忆]
- **热更作废**：原生代码在 apk 里，改一行解析逻辑就要重新出包

### 4.4 如果真要做，建议架构

**B为主 + C为辅**，别把 C 当主线：

```
C 收到通知
  → 解析成「候选交易」 → 置信度评分
  → 高置信（金额 + 商户名 + 支出词都齐）
       → 进「待确认」列表，不直接入账
  → 低置信 → 丢弃

用户打开 App
  → 首页顶部一张卡片「有3 笔待确认」（复用你现有的 .rise-in 动画）
  → 批量确认 / 批量改分类 → 写入
  → 与 CSV 导入共用同一套去重 + 分类逻辑
```

这比「静默自动入账」安全得多 —— **用户看到并确认过，才算真账**。少了确认环节，一笔误判的 500 元支出会毁掉用户对整个 App 的信任。

## 6. 与项目定位的取舍

你的 App 核心卖点是**数据只存本地、不联网不上传**。

| 方案 | 对这个卖点的影响 |
|---|---|
| B 账单导入 | ✅ **零影响**。全程本地，用户主动选文件 |
| C 通知监听 | ⚠️ **不联网，但改了发版链**。热更优势作废 |
| 云端 LLM 解析 | ❌ **直接破坏卖点**。不要做 |

所以从产品一致性看，B 是唯一无代价的方案。

1. **微信 CSV 在 App 端的编码与换行**：社区项目普遍说 UTF-8，但实际文件带 BOM、CRLF 的情况未验证。`plus.io` 读文件后要不要去 BOM 必须测。
2. **`交易时间` 精度**：CSV 里精确到秒，你现有 `occurred_at` 是毫秒 —— 补 000。
3. **XLSX 格式**是否与 CSV 完全同列。未确认，建议不支持。
4. **通知文本的具体句式**：第4.2 节列的几个格式来自社区项目描述，未在HyperOS 3.0 真机上抓过。
5. **「用于个人对账」能否导出最近两天**：有资料说不支持最近两天，另有资料说支持。未确认 —— 如果真不支持，用户当月记账会有 1-2 天的延迟。
6. 微信是否提供「个人账单订阅推送」的隐藏入口。找不到任何官方文档。
