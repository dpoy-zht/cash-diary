## 3. 逐项目分析

### 3.1 BeeCount 蜜蜂记账 · 2536★

**简介**（README + topics 实测）：本地优先跨端记账，iOS/Android/Web 三端；自建云 + iCloud/WebDAV/S3 同步；AI 记账；MCP 协议。创建于 2025-09-06，一年做到 2536★，是**功能重合度最高的一个**。

**核心功能**：多账本、标签与预算、周期记账（对应你的固定支出）、账户管理与转账自动平账、统计图表、应用锁 + 生物识别、AI 记账（语音/图片/对话）。

**⚠️ 许可证是自定义非商用协议，这是本次调研最重要的发现**。我实际读了 `LICENSE`：

```
授权范围
  非商业使用（免费）：个人使用 / 学习研究 / 非营利组织 / 开源贡献
  商业使用（需付费授权）：
    1. 作为商业产品或服务的一部分提供给客户
    2. 在商业环境中为盈利性组织服务
    3. 基于本软件开发商业产品或提供商业服务
    4. 集成到商业软件中
    5. 提供基于本软件的付费云服务或 SaaS
使用条款：保留版权声明 / 修改版必须公开源码 / 禁止移除标识
```

**结论：技术上可学，法律上不能抄。** 它不是 OSI 认定的开源协议，你直接复制代码进自己的项目 → 违反「修改版本必须公开源代码」；你把它当竞品抄功能也要小心（功能本身不受保护，但实现细节受保护）。**只读不改、只学思路，是最安全的用法。**

**关键差异 vs 你的项目**：
| | BeeCount | 奶蛙记账 |
|---|---|---|
| 技术栈 | Flutter/Dart | uni-app + Vue3 |
| 平台 | iOS + Android + Web | 仅 Android（+H5） |
| 存储 | 本地 + 可选云同步 | 纯本地 |
| 自动记账 | AI 视觉/文本识别（需配 API Key） | 无 |
| 分类 | 多级（未见严格两级限制） | 严格两级 |
| 发版 | 应用商店 | GitHub Releases + wgt 热更 |

**值得借鉴的三点**（都读了源码）：

**① 微信/支付宝账单 CSV 导入器 —— 这正好是你上一轮分析的 B 路线，它有完整实现。**

`lib/services/import/parsers/wechat_parser.dart` 表头定位策略：
```dart
// 优先关键词定位，兜底走列数一致性规则
final keywordIndex = _findHeaderRow(rows, ['交易时间', '交易类型']);
if (keywordIndex != null) return keywordIndex;
return super.findHeaderRow(rows);
```
前 30 行里找同时含「交易时间」「交易类型」的行当表头 —— 不假设固定在第 17 行，这比我上一轮文档里写的「前 16 行元信息」稳健得多。**建议你按这个改。**

`lib/services/import/csv_parser.dart` 里两个细节值得抄：
```dart
// 规范化换行并移除 UTF-8 BOM  ← 我上一轮列为「未确认项」，这里给出了确定答案
var text = input.replaceAll('\r\n', '\n').replaceAll('\r', '\n');
if (text.isNotEmpty && text.codeUnitAt(0) == 0xFEFF) {
  text = text.substring(1);
}
```
分隔符自动检测（逗号 > 制表符 > 分号 > 竖线 > 空格），且**不进入引号内部统计**——支付宝旧版 CSV 在字段里混 tab，不跳过引号会误判。

**② `generic_parser.dart` 的列名归一化，可以直接照搬成你的字段映射表**：
```dart
// 中文匹配（顺序有讲究：先长后短，避免「交易类型」被「类型」抢先匹配为 type）
if (_containsAny(s, ['二级分类', '子分类', '次分类', 'Subcategory'])) return 'sub_category';
if (_containsAny(s, ['分类', '类别', '账目名称', '科目', '交易分类', '交易类型'])) return 'category';
// 先匹配转出/转入账户，再匹配通用「账户」
if (_containsAny(s, ['转出账户', 'From Account'])) return 'from_account';
if (_containsAny(s, ['转入账户', 'To Account'])) return 'to_account';
if (_containsAny(s, ['账户', 'Account'])) return 'account';
```
**注意它对交易单号的处理和我上一轮的结论冲突**：它把「交易单号/订单号/编号」明确 `return null` 忽略掉了，即**不做基于交易单号的去重**。这是它的设计选择（靠其他方式去重），但我认为你的场景应该保留 `交易单号` 做去重键——它更可靠。这点上别照抄。

**③ 自动记账的防重复机制**（`lib/services/automation/auto_billing_config.dart`）：文件等待超时 3s、同路径 5s 内只处理一次、已处理缓存上限 100 条、截图文件最长有效期 5s。这套参数化的超时常量表值得直接搬——**和你项目里 `backup-file.js: withTimeout()` 是同一个思路**（你那边是 `plus.io createReader()` 在 vivo 上永久挂起，它这边是截图文件写入延迟）。

### 3.2 ezbookkeeping · 5751★

**简介**：自托管个人理财应用，Go 后端 + Vue/TS 前端 + 移动端 App。MIT 协议。

**核心功能**：二级分类（带 `subCategories` 嵌套响应）、多账本、交易模板、交易标签（带标签组）、图片附件、导入导出、双因素认证、自定义图标、WebDAV/网盘备份。

**⚠️ 它是自托管 Web 应用，不是手机原生 App**，和你的形态差别大。但它的**数据模型设计是你最值得参考的**——我读了 `pkg/models/transaction_category.go`：

```go
// LevelOneTransactionCategoryParentId represents the parent id of level-one transaction category
const LevelOneTransactionCategoryParentId = 0

type TransactionCategory struct {
	CategoryId       int64 `xorm:"PK"`
	Uid              int64 `xorm:"INDEX(IDX_category_uid_deleted_type_parent_category_id_order) NOT NULL"`
	Deleted          bool  `xorm:"INDEX(IDX_category_uid_deleted_type_parent_category_id_order) NOT NULL"`
	Type             TransactionCategoryType   // 收入/支出/转账 三类
	ParentCategoryId int64 `xorm:"INDEX(...) NOT NULL"`
	Name             string
	DisplayOrder     int32 `xorm:"INDEX(...) NOT NULL"`
	Icon             int64
	Color            string `xorm:"VARCHAR(6) NOT NULL"`   // 6位十六进制
	Hidden           bool
	Comment          string
	CreatedUnixTime  int64
	UpdatedUnixTime  int64
	DeletedUnixTime  int64
}
```

**和你项目的分类模型几乎一模一样**，只有两个差异值得注意：

| 维度 | ezbookkeeping | 奶蛙记账 |
|---|---|---|
| 一级标识 | `parent_id = 0`（哨兵值） | `parent_id IS NULL` |
| 分类类型 | `type` 区分收入/支出/转账 | 收入/支出分类分开存放（推测） |
| 排序 | `display_order` 独立字段 | 未确认 |
| 删除 | `deleted` 布尔 + `deleted_unix_time` | `deleted_at` 毫秒戳 |
| 颜色 | 6 位 hex 字符串独立字段 | 按 icon key 取色 |

**「`parent_id = 0` vs `NULL`」这个选择有现实影响**：NULL 在 SQL 里三值逻辑，`parent_id = 0` 判断更直观；但 NULL 在「未分类/无上级」语义上更标准。你已用 NULL 就别改了（迁移成本 > 收益），但**要知道别人选了另一条路，不是唯一解**。

**它的索引设计值得抄**：`IDX_category_uid_deleted_type_parent_category_id_order` 是**多列复合索引**，把「用户 + 软删 + 类型 + 父级 + 排序」合成一个。你的 `category` 表如果按「查某个用户某类型的所有一级分类并排序」这种模式查，单列索引会慢。**这条对你有直接价值**——尤其是 `parent_id` 上的索引。

**响应体带 `SubCategories` 嵌套**（`omitempty`），前端拿到的就是树，不用自己拼。你的 `services/category.js` 应该是平铺返回、前端组装？如果是，可以评估改成后端/服务层直接出树，少一层前端逻辑。

### 3.3 MyExpenses · 1189★

**简介**：GPL-3.0，Kotlin 原生，**2012 年创建，14 年老项目**，仍然每天有提交。这是整个列表里唯一「久经考验」的。

**核心功能**（README）：收支记录、多账户 + 币种转账、周期交易计划（对应你的固定支出）、QIF/CSV 导入导出、密码/锁屏保护、主题与字号自定义、账单对账。

**目录结构实测**（`myExpenses/src/main/java/org/totschnig/myexpenses/`）值得注意：
```
db2/              ← 数据库层独立成模块
model2/           ← 数据模型
provider/         ← ContentProvider
sync/             ← 同步（WebDAV/Dropbox/OneDrive/Drive）
ocr/  tesseract/  ← 自带 OCR（tesseract + mlkit 多语言模型）
sqlcrypt/         ← SQLCipher 加密数据库
transactionscontract/  ← 对外契约（供其他 App 调用）
```

**关键差异**：它做了 `sqlcrypt/`（SQLCipher 加密库）和 `transactionscontract/`（ContentProvider 契约）。你项目是明文 SQLite + 无对外契约——这是「隐私优先」和「互操作」两条不同路线。**如果你将来想给省心记小程序或别的东西供数据，`transactionscontract` 这个目录的思路可以参考**（不过 uni-app 里做 ContentProvider 需要原生插件，成本高）。

**GPL-3.0 的商用含义**：允许商用、允许收费，但** copyleft **——如果你分发基于它的修改版，必须同样以 GPL 开源。你只是「读代码学思路」完全没问题（GPL 不限制阅读），但**不要把它的代码片段直接粘进你的项目**，否则你的项目可能被传染成 GPL。你的项目目前是公开仓库（`dpoy-zht/cash-diary`），如果没声明协议，建议补一个 MIT/Apache-2.0——这也顺便避免将来扯皮。

**值得借鉴**：14 年的迁移经验。它有 `ChangeLog/` 目录逐个版本记录。你的 `MIGRATIONS` v1–v7 只追加的约定是对的，**它的长期演化的一个启示是：迁移写清楚「为什么改」比「改了什么」更重要**。你现在的 `schema.js` 注释可以加强。

### 3.4 pennywiseai-tracker · 574★

**简介**（README）：自动读取交易短信 + 端侧 AI（MediaPipe）整理成财务数据，无手动录入、无云端处理。创建于 2025-07，一年 574★。

**⚠️ AGPL-3.0 协议**（我读了 `LICENSE`，不是常见的 GPL/MIT）。AGPL 比 GPL 更严：**即使用户只是通过网络使用你的服务，也必须提供源码**。对 App 来说影响和 GPL 类似（App 是本地分发），但**如果你将来给它加任何联网服务端，AGPL 会把服务端也要求开源**。

**它做的正好是你上一轮分析的「C 路线」的一个变体**：读**短信**而不是读通知。

**这个区别很重要**：
| | 通知监听 | 短信监听 |
|---|---|---|
| 权限 | `BIND_NOTIFICATION_LISTENER_SERVICE` 特殊权限 | `READ_SMS`/`RECEIVE_SMS` 普通运行时权限 |
| 微信支付 | ✅ 微信支付会推通知 | ❌ 微信支付**不发短信** |
| 银行 | 部分银行有 App 通知 | ✅ 银行普遍发交易短信 |
| 厂商限制 | HyperOS/vivo 杀后台 | 相对宽松 |

**对你有直接价值**：你的用户如果用银行卡消费，短信是比微信通知更可靠的通道；而微信支付只有通知一条路。**但它证明了「自动入账」在开源社区是有人做且能做出来的**，不是我上一轮说的那么悲观——我上一轮说「没有任何一条路能做到」，现在要修正为：**短信路线可以做到近实时自动入账，但覆盖不到微信支付**。

**值得借鉴**：端侧 AI 解析（MediaPipe）而不是调云端 LLM。这守住了「数据不出本地」。但它要打包模型文件（会增大 APK），且 uni-app 里做不了——**这条对你不可行，除非愿意写原生插件**。

### 3.5 SimpleAccount 简帐 · 109★

**简介**：uni-app 框架开发的本地记账应用，无联网、数据全本地。MIT 协议。**这是技术栈和你最接近的一个。**

**目录结构实测**：
```
App.vue / main.js / pages.json / manifest.json    ← 标准 uni-app
pages/
  add/            ← 记一笔
  index/          ← 首页
  statistics/     ← 统计
  budget-manage/  ← 预算管理
  category/  category-detail/  category-manage/   ← 分类（三级页面结构）
  chat/           ← AI 对话记账
  ai-config/  voice-config/                        ← AI / 语音配置
  icon-manage/    ← 图标管理
  profile/        ← 我的
```

**⚠️ 它的存储是 `uni.getStorageSync`，不是 SQLite**。我读了 `pages/budget-manage/budget-manage.vue`，所有数据都是 `uni.getStorageSync('records')` / `uni.getStorageSync('categoryBudgets')` 全量数组 + 前端 filter/reduce 计算。

**这是它最大的短板，也正是你已经跨越的地方**：
- 全量数组在内存里 filter，几百条还行，几千条开始卡
- `getRecordsByTimeUnit()` 每次调用都 `uni.getStorageSync('records')` 读一遍全量再 filter —— O(n) 全表扫
- 分类是 `uni.getStorageSync('expenseCategories')` 的硬编码兜底数组（餐饮/交通/购物… 10 个）
- 金额用 `parseFloat(amount).toFixed(2)`，**浮点**，没有整数分
- Options API，不是 `<script setup>`

**但它的预算功能比你的完整**，值得抄的是**产品设计**不是代码：

**① 预算支持日/月/季/年四种时间单位**，且季度可以自定义起始月份：
```js
timeUnits: [
  { key: 'day',     name: '日',  factor: 30 },
  { key: 'month',   name: '月',  factor: 1 },
  { key: 'quarter', name: '季',  factor: 1/3 },
  { key: 'year',    name: '年',  factor: 1/12 }
]
// 季度跨年处理：11-1月、12-2月 要判断 recordYear === currentYear + 1
```
你的 `budget` 表按月存，**没有多周期概念**。这是个真实的功能差距。

**② 预算健康度评分 + 月末超支预测**：
```js
// 日均支出 → 线性外推预测月末
dailyAverage = usedAmount / currentDay
projectedAmount = dailyAverage * daysInMonth
// 健康度分档：>100% 得 max(0, 50-(超支%)*2)，>90% 得60，>80% 得80，>70% 得90
```
**「预计月末支出」这个指标很实用**，比单纯显示「已用 60%」更早给出预警信号。实现只要几行，建议加。

**③ 分类预算的进度条分档配色**：≤70% 绿、≤90% 橙、>90% 红。和你首页的分档思路一致。

### 3.6 expensemanager · 154★

**简介**（官网 + README）：Kotlin + Jetpack Compose + Clean Architecture + MVVM，Room/SQLite 本地存储，100% 离线。**Apache-2.0**（我读了 `LICENSE`）。

**核心功能**：收支与转账、多账户、150+ 币种、分类预算 + 超支预警、图表、生物识别锁、CSV 导出、记账提醒、深浅主题。

**相似度中等**：功能面比你小（无多账本、无固定支出、无两级分类），但它是**架构最干净的参考**。Clean Architecture + MVVM + Room + Hilt 分层，对「Android 原生该怎么分层」是标准答案。

**对你的价值有限**——你的 uni-app 栈用不上 Room/Hilt/Compose。**唯一值得抄的是它的「记账提醒」**（每日推送提醒用户记账，防止漏记）。你已经有 `fixed_expense` 补记，但「今天还没记账」这种轻提醒是另一回事，uni-app 里用 `plus.push` 或本地通知能做。

**Apache-2.0 是全场最友好的协议**：允许商用、允许闭源修改、允许不公开源码、只需保留版权声明和 NOTICE。如果你想从某个项目「借鉴代码结构」，优先找 Apache-2.0 的。

## 5. 结论与建议

### 最值得参考的 1 个项目：**ezbookkeeping**

**理由**：
1. **MIT 协议，可以放心抄代码**（BeeCount 是自定义非商用，MyExpenses/verifin 是 GPL， pennywise 是 AGPL——只有 ezbookkeeping 和 SimpleAccount、expensemanager 是「抄了不传染」的）
2. **数据模型和你的几乎同构**（两级分类 + 软删 + 毫秒时间戳 + 排序字段），`transaction_category.go` 可以直接对照着改你的 `schema.js`
3. **复合索引 `IDX_category_uid_deleted_type_parent_category_id_order` 对你有直接性能价值**
4. 5751★ + 每天提交，经过了大量真实用户验证

**具体动作**：把 `pkg/models/transaction_category.go` 和 `pkg/models/transaction.go` 读一遍，对照你的 `db/schema.js`，重点看：① `display_order` 你缺不缺 ② `hidden` 字段你有没有 ③ 复合索引要不要加。

### 第二值得参考：**BeeCount（只学思路，不抄代码）**

**理由**：它的 `lib/services/import/parsers/` 三件套（`csv_parser.dart` + `wechat_parser.dart` + `generic_parser.dart`）**就是你上一轮那份《微信支付自动入账可行性分析》里 B 路线的完整参照实现**，而且已经踩过 BOM、CRLF、分隔符歧义、表头定位这些坑。

**⚠️ 但它的许可证禁止你复制代码**。正确用法：**读懂它的设计决策，自己用 JS 重写**。可以抄的：
- 表头用「关键词定位 + 列数一致性兜底」，不写死行号
- 先剥 BOM 再 normalize 换行
- 分隔符自动检测且跳过引号内部
- 列名归一化要「先长后短」（`交易类型` 先于 `类型`）
- 超时/去重参数集中成一个 Config 常量类（和你 `withTimeout()` 一个思路）

**明确不要抄的**：它忽略 `交易单号`（`return null`）导致去重靠猜——你反而应该用交易单号做去重键。

### 一句话总结

> **数据模型学 ezbookkeeping（MIT，可抄），账单导入学 BeeCount（非商用，只能学思路），预算产品设计学 SimpleAccount（MIT，但别看它代码只看功能列表）。**

### 顺带发现的一个空档

这批项目里，**没有一个同时做到**：uni-app 栈 + 纯本地无云 + 两级分类 + 多账本 + 固定支出 + 预算 + wgt 热更。SimpleAccount 栈对但功能浅，BeeCount 功能全但栈不同且非商用协议，ezbookkeeping 模型好但是 Web 服务端形态。

**你的项目在这个交叉点上是独特的。** 这对外传播（朋友圈/README）是个可以讲的差异点——但注意措辞，别去贬低其他项目。
