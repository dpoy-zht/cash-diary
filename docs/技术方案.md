## 1. 技术选型总览

| 层次 | 选型 | 理由 |
|---|---|---|
| 跨端框架 | **uni-app（Vue3 + Vite）** | 一套代码出 Android APK，预留微信小程序；Vue3 与学习者现有路线重合 |
| 开发工具 | **HBuilderX** | 官方 IDE，真机运行/云打包一站式，对初学者最省事 |
| 语言 | **JavaScript**（非 TS） | 降低起步摩擦；关键模块用 JSDoc 注释补类型说明，后续可平滑迁移 TS |
| 状态管理 | **Pinia** | Vue3 官方推荐，比 Vuex 简洁 |
| 本地数据库 | **SQLite（HTML5+ `plus.sqlite`）** | App 端原生 SQLite，支持 SQL 聚合，离线优先的事实源 |
| 图表（阶段2） | uCharts / qiun-data-charts | uni-app 生态最成熟 |
| 单元测试 | **vitest** | Vite 原生集成，速度快 |
| 同步后端（阶段4，二选一） | uniCloud（默认）/ FastAPI + MySQL（备选） | uniCloud 免运维；FastAPI 利用团队既有经验 |
| 版本控制 | Git（本仓库） | 规范见根目录 `AGENTS.md` |

**重要平台边界（务必知道）**：`plus.sqlite` 仅在 App 端（Android/iOS）可用；H5 和小程序端没有本地 SQLite。MVP 目标就是 Android App，不受影响；将来出小程序版时，数据访问走 uniCloud 云数据库——这正是本方案"存储适配层"存在的意义（见 §6）。

## 2. 总体架构

### 2.1 分层

```
┌──────────────────────────────────────────────────┐
│ 表现层  pages/ + components/                        │  三页面 + 公共组件，只做展示与收输入
├──────────────────────────────────────────────────┤
│ 状态层  stores/（Pinia）                            │  响应式状态与动作编排
├──────────────────────────────────────────────────┤
│ 业务层  services/                                   │  记账规则、预算校验、聚合计算（纯函数）
├──────────────────────────────────────────────────┤
│ 数据层  db/（schema + migrations + repository）     │  SQL 封装，页面永不直接写 SQL
├──────────────────────────────────────────────────┤
│ 存储适配 adapter/                                   │  阶段1：SQLite 适配器
│                                                     │  阶段4：+ 云端适配器（uniCloud/FastAPI）
└──────────────────────────────────────────────────┘
```

**依赖规则**：上层只依赖下层；同层不互相调用。换存储方案（SQLite → 云端）时只动 adapter 与 repository 的实现，页面与业务层零改动。

### 2.2 数据流（以记账为例）

```
用户点"完成"
  → pages/quick-add 收集 {amountStr, categoryId, note, date}
  → services/tx.add()  校验并换算为分 → 构造记录对象
  → stores/tx.add()    调 repository 落库 → 成功后更新响应式列表
  → 页面 Toast"已记一笔"（保留类型/分类，清空金额，支持连续记账）
```

**原则**：页面不做计算，只收集输入和展示状态；一切金额/时间换算集中在 services 与 utils。

## 4. 数据层设计

### 4.1 数据库封装（db/index.js）

uni-app 的 `plus.sqlite` 是回调式 API，第一步先 Promise 化封装：

```js
// 对外暴露的最小接口（签名示意）
openDB()                          // 打开 _doc/cash-diary.db（首次自动创建）
exec(sql, args)                   // 执行写操作（INSERT/UPDATE/DELETE），返回 Promise
all(sql, args)                    // 查询多行 → Promise<Array>
transaction(fn)                   // 多步写入包事务，失败整体回滚
getUserVersion() / setUserVersion(n)  // 迁移机制钩子
```

**迁移机制**：SQLite 自带 `PRAGMA user_version`。启动时读取版本号，按 `migrations/` 里编号顺序执行未跑过的脚本，逐版本 +1。保证老用户升级 App 后表结构平滑演进。

### 4.2 表结构（db/schema.sql）

```sql
CREATE TABLE IF NOT EXISTS category (
  id      INTEGER PRIMARY KEY AUTOINCREMENT,
  name    TEXT NOT NULL,
  type    TEXT NOT NULL CHECK (type IN ('income','expense')),
  icon    TEXT NOT NULL DEFAULT '',
  sort    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE IF NOT EXISTS transaction_record (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  category_id  INTEGER NOT NULL REFERENCES category(id),
  type         TEXT NOT NULL CHECK (type IN ('income','expense')),
  amount_cents INTEGER NOT NULL CHECK (amount_cents > 0),
  note         TEXT NOT NULL DEFAULT '',
  occurred_at  INTEGER NOT NULL,   -- 毫秒时间戳
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER             -- 软删除；NULL = 有效
);
CREATE INDEX IF NOT EXISTS idx_tx_time ON transaction_record(occurred_at);
CREATE INDEX IF NOT EXISTS idx_tx_del ON transaction_record(deleted_at);
```

约束即文档：`CHECK` 把"金额必须为正整数分""类型只能是 income/expense"钉死在数据库层，业务层校验只是 UX 防线。

### 4.3 仓储层接口（db/repository/tx.js）

```js
listByMonth(year, month)      // 当月份有效流水（deleted_at IS NULL），按 occurred_at 倒序
monthSummary(year, month)     // { expenseCents, incomeCents } 由 SQL SUM(CASE WHEN…) 一次算出
insert(record)                // 返回新 id
update(id, patch)             // 同步刷新 updated_at
softDelete(id)                // UPDATE deleted_at = now()
```

聚合必须发生在 SQL 侧（`GROUP BY` / `SUM`），不在 JS 里循环累加——数据量上来后的性能底线。

### 4.4 金额与时间工具（utils/）

```js
// utils/money.js —— 唯一允许碰金额换算的地方
parseAmountToCents('19.9')   // → 1990（非法输入返回 null）
formatCents(1990)            // → '19.90'
formatSigned(1990, 'expense')// → '-¥19.90'（千分位）

// utils/date.js
monthRange(year, month)      // → [月初毫秒, 月末毫秒+1)
dayLabel(ts)                 // → '今天 9月24日 周三' / '昨天 …' / '9月22日 周一'
ymOf(ts)                     // → '2026-09'
```

**三条铁律**（违反即返工）：金额一律整数分；时间一律毫秒时间戳、展示时才本地化；删除一律软删除。

## 5. 状态层与页面实现要点

### 5.1 Pinia Store 划分

| Store | 职责 |
|---|---|
| `useTxStore` | 当前查看月份的流水数组、月合计、增删改动作（动作内调 services，成功后写回 state） |
| `useCategoryStore` | 分类列表（按 type 过滤的派生数据）、首次启动初始化内置分类 |
| `useMetaStore` | 当前查看的年月（明细页左右切换用） |

派生数据用 `computed`（如按天分组），不把"分组后的结构"存进 state。

### 5.2 关键交互的实现思路

**数字键盘（money-keyboard）**：维护字符串 `amount`，规则与 PRD §6.1 一致（整数 ≤9 位、小数 ≤2 位、首位小数点前补 0）。组件只抛事件 `on-input(str)` 与 `on-confirm`，状态归父页面——保证编辑弹层复用同一套输入逻辑。

**连续记账**：`confirmAdd` 成功后仅清空金额与备注，保留收支类型与已选分类（PRD 刻意设计）。

**编辑弹层（edit-sheet）**：底部抽屉，props 传入记录快照，本地编辑，"保存"时调 `services/tx.update`；删除二次确认（PRD 规范）。日期不可改（MVP 冻结范围）。

**明细按月分组**：列表查询 SQL 按月份过滤后，前端用 `utils/date.js` 的 `dayStart` 分组渲染"今天/昨天/M月D日"标题。

## 6. 同步扩展预留（阶段4 才实现，现在只立接口）

adapter 层定义统一契约，阶段 1 只有 SQLite 实现：

```js
// adapter 契约（示意）
pullChanges(since)     // 拉取远端变更
pushChanges(list)      // 推送本地变更（幂等：以记录 id + updated_at 为准）
```

阶段 4 增加 `adapter/cloud.js`（uniCloud 云函数或 FastAPI 接口），同步引擎"本地变更队列入队 → 网络可用时推 → 拉远端新变更 → 按 `updated_at` 取新者合并（last-write-wins）"。因 MVP 已软删除，删除同步天然可行。`plus.sqlite` 不跨端的问题也在此层消化：小程序版用云数据库适配器，业务层无感。

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| `plus.sqlite` 只在 App 端可用，调试期想在浏览器里跑不起来 | 中 | 数据访问全走 adapter/repository，H5 调试时可临时换内存实现；日常以真机为准 |
| HBuilderX 云打包需 DCloud 账号实名 + 排队 | 低 | 阶段 0 提前注册认证；自用 APK 用云打包即可 |
| 真机与模拟器行为差异（通知、权限） | 中 | 通知/权限类功能（阶段2）一律真机验证 |
| 数据库迁移写错损坏用户数据 | 中 | 迁移脚本只增不改；每个迁移先备份旧表再建新表拷贝 |
| 记账键盘输入边界 bug（连点小数点等） | 中 | 输入逻辑抽纯函数，用 vitest 覆盖全部边界用例 |
